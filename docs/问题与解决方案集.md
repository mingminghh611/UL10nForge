## A. 写回安全问题（最高优先级）

### A1. 写回后按键消失/失灵——按钮 m_Name 与显示文本同值被改对象名
- **现象**：写回后「开始/设置/退出」按钮 UI 失灵、游戏卡死无法推进（多游戏实证 2026-08-15）。
- **根因**：按钮对象 `m_Name` 与 `m_text` 同值（"Exit"/"Settings" 等显示词）。rawstr 字节扫描无字段身份，名字+文本两处一起被判 display 翻译写回 → 对象名被改 → 游戏代码按名查找（Find/事件/动画）断裂。
- **解决方案（双层修复）**：
  1. 提取层（`extractor.py`）：代码对象/组件对象中白名单词同值出现 ≥2 处（名字+文本共享结构）→ 全组 `structural` 跳过（reason=`object_name_shared_word`）；单次出现照常翻译。
  2. 写回层（`logic_audit.py`）：`code_heavy_display_word` + `LOGIC_COMPARE_WORDS` + obj_strings 同值 ≥2 → 确定性回退保留原文（`display_word_shared_with_object_name`）；`audit_repeat_consistency` 组内 structural+translated 混排自动全组回退。
- **原则**：宁漏勿坏——此类词几乎都有本地化表副本可翻；写坏对象名是灾难。
- **记忆**：[[button-name-writeback-bug]]
- **检查点**：写回后必须验证 changed MonoBehaviour 的 `m_Name` 0 变化（`tmp_typetree_diff.py`）。

### A2. 背景音乐消失——FMOD 配置类写回兜底依赖 externals 兄弟文件
- **现象**：写回后背景音乐/BGM 消失。
- **根因**：FMOD 配置对象（`fmod_config_object` 类）的语义判定依赖 `_script_class_from_head` 通过 m_Script PPtr 补载同目录 .assets 解析类名。若 externals 兄弟文件不在场，函数静默返回 `''` → semantic_revert=0 → 译文照写 → 配置字段被改写。
- **解决方案**：真实写回走 `copy_game_dir` 全量复制 → 兜底生效；测试/回归必须复制整个 Data 目录的全部 .assets，孤立单文件复现的「失败」结论不可信。模拟旧库条目要在 meta 带 `disposition: translate` 才能走到 `logic_key_evidence` 的 fmod 分支（否则被 `legacy_key_guard` 拦截）。
- **记忆**：[[fmod-writeback-fallback-externals]]
- **检查点**：写回后对象级 diff 中音频/配置对象必须 0 变化。

### A3. CSV 对话表误判 YAML 致黑屏
- **现象**：游戏启动黑屏（Rendezvous 实证 2026-08-17），Player.log 显示 CSVParser 数组越界崩溃。
- **根因**：CSV 表头首列空格 + 对话行含冒号 → `looks_like_yaml_text` 误判 YAML → yaml 按行号重建丢表头 → CSV 列/行错位 → 游戏解析越界。
- **解决方案**：
  - CSV 判定必须排 yaml 前；`looks_like_yaml_text` 硬排除 CSV
  - yaml 条目不做代码行过滤；`apply_format_text` yaml 分支行数守恒保护（重建行数 != 原文行数 → 返回原文宁漏勿坏）
  - `_patch_textasset` yaml 组预检（旧库 yaml 条目丢行 → 整组 rejected `yaml_line_loss_guard`）
- **记忆**：[[yaml-csv-misjudge-black-screen-lesson]]
- **检查点**：黑屏排查先看 Player.log 崩溃栈，别只查 level 文件字节。

### A4. 写回后地毯式审计（通用任意格式）
- **两层审计**（`writeback_audit.py`）：
  - 第 1 层确定性硬闸门（任何 FAIL → needs_rewrite 阻断发布）：字节层（编码/BOM/EOL 守恒）+ 行数守恒 + 结构守恒（JSON 深比树/XML 元素树/CSV 首列/PO msgid/字幕时间码）+ 条目级占位符（{0}/%s/%1$s/{name}/<b>/\n）+ 渲染一致性（store 渲染 bytes == 磁盘写回）
  - 第 2 层审校模型软复核（只审计第 1 层 PASS 且有差异的文件），只记 flag 供人工确认
- **要点**：writer 键字段保护优先（`_KEY_FIELD_NAMES` 含 color/sound/type 等）；markdown marker 守恒；富文本标签豁免；JSON 转义误报抑制。
- **记忆**：[[writeback-audit-generic]]
- **检查点**：写回后自动跑 audit_writeback，needs_rewrite=True 需重写回。

### A5. KoiKoi 写回排查结论（2026-09-01）
- **现象**：用户报「写回后按键消失、背景音乐消失、UI 莫名消失、按键失灵」。
- **调查结论**：写回机制本身安全——m_Name 0 变化、音频对象 0 变化、字体替换正常（legacy Font 48/49/90 → NotoSerifCJKsc）。**真实问题在翻译质量**：
  - obj 127 卡牌名乱翻（Hagi→哈吉、Botan→植物学、Susuki→苏苏基）
  - 幻觉译文（'Botan no AoTan'→'[来源文件] KoiKoi_Data/sharedassets0.assets'）
  - 逻辑标识被翻：obj 2099/2114/2120/2135 的 "Load"（位于 m_MethodName 值 'LoadLevel, Assembly-CSharp' 附近）被译成 负载/读取
  - 错误翻译：'Deck Play'→牌组播放、'Call Koi Koi'→拨打 Koi Koi、'Sounds'→听起来、'Draw'→绘制
- **解决方案**：
  1. 翻译质量 = 写回安全的一部分，必须同时治理
  2. 幻觉译文拦截（译文含"[来源文件]"/路径痕迹 → 拒绝）
  3. m_MethodName 附近字符串保护（逻辑绑定标识不译）
  4. 卡牌术语词库（花札术语表，KoiKoi 专属 BUILTIN）
- **检查点**：所有 changed 对象必须是目标对象；字符串 diff 中不得出现原文消失但译文与原文语义无关的情况。

### A6. 渲染一致性 font_enabled 参数
- **现象**：4 个 .subs 文件 render_consistent 误判 FAIL。
- **根因**：`writer._render` 字体启用时对未译条目做标点归一化，audit `_render_from_store` 未传 `font_enabled` → 同源不一致。
- **解决方案**：`_render_from_store` 补 `font_enabled` 参数同源。
- **检查点**：写回审计渲染一致性要与 writer 同源同参数。

### A7. 写回链路全量审计结论——六层防线逐层验证（2026-09-04，0.38.0 任务4）
- **背景**：用户报「写回后概率出现游戏性 bug」（列举形态：场景卡顿/背景音乐消失/按键消失/UI 消失/场景加载失败/按键失灵/卡死），要求重点加强写回模块。对 `writer.py`（2029 行）、`logic_audit.py`（578 行）、`il2cpp_writeback.py`、`record_writer.py` 全文逐行审计。
- **审计结论：未发现新的确定性漏网路径**。六层防线逐层确认闭合：
  1. **L1 入口门**：`is_write_ready` → `_should_write_entry`（disposition 权威分支，仅 translate 写；localization/role 白名单；us/il2cpp 过 is_code_identifier；legacy guards 仅旧库）。
  2. **L2 写前拦截**：immutable_field_protected（18 字段含 m_Name/m_ControlPath/m_Action/m_ActionMap）、field_path_value_mismatch（current != original 拒）、TextAsset 非 UTF-8 整文件拒（F3）、yaml 行数守恒预检、ink 控制词硬保护、xml CDATA/DOCTYPE 拒（F7）、Addressables CRC 写前预检（源 CRC 必须唯一命中）。
  3. **L3 语义回退**（logic_audit）：type_descriptor / unityevent_binding / obj_is_input_axis / fmod_event_path / fmod_config_object / logic_key_in_code_object / display_word_shared_with_object_name + typetree 字段路径 UnityEvent 信号 + audit_repeat_consistency 组内一致化 + 写回侧 `_mono_object_name_span`（m_Name 跨度兜底）与 `_script_class_from_head`（配置类兜底，旧库 meta 缺失也回退）。
  4. **L4 补丁白名单预演**：`_assert_asset_diff_whitelist`——原位补丁 diff 严格落 span 并集；变长补丁非目标区段子串顺序保留 + 短段漂移 ≤ max_shift 预算。
  5. **L5 重开六重验证**：目标字节 + baseline 全对象 sha256 + immutable 逐值 + C2 非目标叶子 + verify_logic_layer（长度头自证/译文存在性/序列对齐走查）+ DLL #US / IL2CPP C3 全池比对——任何失败整文件拒绝、副本原样。
  6. **L6 编排/原子性**：WriteResult 四态记账（written/rejected/logic_reverted 必须 resolved）+ 尾部兜底未 resolve → rejected + 同卷 TemporaryDirectory + `_atomic_write_bytes`（mkstemp+fsync+os.replace+重试）+ Addressables catalog 写后 CRC 回写（唯一性校验 + 失败回滚）。
- **用户列举故障形态 → 防线映射**（全部闭合）：
  | 故障形态 | 防线 |
  |---|---|
  | 场景卡顿 | 任务1 已根治（E4：插件 1.5.0 退避 + deploy skip-when-COVERED） |
  | 背景音乐消失 | A2 FMOD config 判定 + fmod_event_path/fmod_config_object 回退 + `_script_class_from_head` 写回侧兜底 |
  | 按键消失/失灵 | immutable 18 字段 + UnityEvent 信号（字段路径+值层）+ m_Name 跨度兜底 + display_word_shared_with_object_name |
  | UI 消失 | C2 非目标叶子快照 + immutable 逐值重开比对 + baseline 全对象 sha256 |
  | 场景加载失败 | Addressables CRC 预检+回写（唯一性+回滚）+ yaml 行数守恒 + TextAsset BOM/编码保真 |
  | 卡死 | verify_logic_layer 序列验证 + diff 白名单 + IL2CPP/DLL 重开全池比对 + 整文件拒绝原子性 |
- **检查点**：写回后必跑 `writeback_audit`（A4）；概率性 bug 排查先按上表映射到防线，再对照写回日志四态记账（written/rejected/logic_reverted 计数），不要先怀疑写回字节层（L4/L5 已把字节级破坏压缩到重开验证必拦）。

## B. 识别与文本分类问题

### B1. 识别哑信号——跳过是哑信号，覆盖率≠遗漏率
- **现象**：UnityScript 程序集整类遗漏 825 条文本（lilys-day-off 实证），0 失败审计仍漏。
- **根因**：被跳过的文本不产生任何可见信号；启发式是在见过的样本上拟合的模式，对未见形态直接失明。
- **解决方案**：
  1. 文本载体形态显式清单化（C#/UnityScript/Boo/IL2CPP/typetree/原始串）
  2. 审计口径升级为召回率（真实文本全集 vs 进池文本）
  3. 扫描报告加形态级 skipped 率告警
  4. 用户实测发现的遗漏 → 真实样本 fixture 资产化
- **记忆**：[[recognition-silent-miss-lesson]]

### B2. SetText 等引擎方法不贡献 code 信号致对象名误译
- **现象**：level0 obj 3311 的 `audio`（GameObject 名）被译成「音频」写回 → 游戏按名查找失败（minato 实证 2026-08-15）。
- **根因**：SetText 在引擎串过滤中不贡献 code 信号 → is_code_heavy=False → 对象名被 display 放行。
- **解决方案**：`_CODE_DRIVEN_METHODS`（SetText/SetActive…）计入 `direct_code_signal_count` → is_code_heavy → 对象名跳过。静态按钮对象（控件状态证据）不受影响（对照组测试锁定）。
- **记忆**：[[minato-round2-fixes]]
- **检查点**：引擎串过滤会吞掉对象级信号——对象判定信号必须在完整 scanned 池上算。

### B3. 多语言词典 19 倍浪费 + 键被译坏
- **现象**：electric-trains 内置 19 张同结构语言词典 TextAsset，旧管线全提取 → 19 倍浪费 + 键被译坏（missions=→任务= 断查找）。
- **解决方案**：组内只提取第一张表、其余留档；KV 行只提取值（键保真）；KV 词典判定要求键含字母。
- **记忆**：[[recognition-corpus-and-il2cpp-dumper]]

### B4. il2cpp 引擎字符串污染（KoiKoi 实证 2026-09-01）
- **现象**：pending 1095 条全 low confidence（il2cpp_sentence 611 条引擎日志 + il2cpp_format_template 484 条引擎模板），自动翻译池接近空 → 每批 1-2 条慢翻译。
- **根因**：il2cpp 引擎字符串（Unity 引擎日志/模板）被识别为可翻译条目但 confidence=low，既不能自动翻译也不该被翻译。
- **解决方案**：
  1. il2cpp_sentence/format_template 分类改进：引擎字符串标 `skipped`（原因=engine_string）而非 low pending
  2. 非 UI/非 display 的引擎日志/模板不进翻译池
  3. 进度发射逻辑保持（done_since_emit>=batch OR 1.5s 节流），但前提是池里有真条目
- **检查点**：翻译页「每批完成条数」应稳定 ≈ batch_size 或真条目吞吐；不要出现长时间 1-2 条。

### B5. CSV 判定顺序（见 A3）
- CSV 判定必须排 yaml 前。

### B6. 识别「不需要翻的不用翻」
- **原则**：识别彻底全面 + 精确筛选需要翻译的问题。署名/来源文本（如 KoiKoi 的音频素材 CC0 许可证署名）不是 UI 文本，不应 disposition=translate。
- **检查点**：扫描结果中署名/许可证/调试日志不应出现在翻译池。

### B8. 结构性文本误识别进队列——翻译前最终兜底闸门（2026-09-02）
- **现象**：工具易把 Key/ID/GUID/路径/文件地址/变量名/类名/资源名/Animator State 等结构性文本识别成待翻译文本；翻译后游戏按键失效/UI 消失/背景音乐丢失/卡顿（与 A1/A2 的写回安全同源，但根因在识别层多路径放行）。
- **根因**：识别有多个提取路径（rawstr 字节扫描 / typetree / mono #US / il2cpp metadata / TextAsset json/csv/kv / ink），各自独立分类，历史上一度出现某条路径把结构文本误标 `role=display` + `disposition=translate` 放行进翻译队列；`is_actionable_translation` 是全部队列入口（翻译页待翻译池 / runner run_scope / 概览计数）的单一权威判定，但它此前只依赖提取层 meta（role/disposition/confidence），对「提取层误标」无兜底。
- **解决方案**：`models.is_actionable_translation` 在**任何队列接纳前**追加原文结构终检 `_final_structural_backstop`——原文命中 `is_hard_structural`（URL/路径/GUID/32位哈希/JSON/程序集限定名/纯数字/版本号/混合符号 token）或 `is_engine_string_core`（确定性引擎串：default sprite asset/字体名/Timeline 轨道/FMOD 事件/InputSystem 绑定/hex）→ 一律拒于队列外，无论提取层为何判定。三处保护防误伤：
  1. 键风格标识符（ui_newGame/MENU_PLAY/Level1）**不在闸门职责**（单 token 是上下文决定，由各提取器 should_skip 分层；Level1/Room2 真关卡/对话框名不误杀）；
  2. DISPLAY_WORDS 白名单豁免（'2d'/'3d' 命中 hex 形态但真 UI 词）；
  3. C# 转义换行（字面 `\n`）是显示模板结构标记，硬结构判定前替换保护（`\r\nSettings\r\n\r\n{0}kg\n£{1:0.00}\r\n` 设置模板必须可译）。
- **实证**：全语料 minato/fromivan/hickory/hrana/doubleshake/a-catfiends/222am/78-hour-rain/alisa-demo/crash-back-in-time/deadbeat/electric-trains/force-reboot/give-me-strength/hotel-paradise 共 15 游戏 actionable 全集实测 → 终检拦 0，**0 误伤**（游戏已由提取层分层正确）；模拟「提取层误把硬结构标 display/high」→ 全部被拦。回归测试 `tests/test_final_structural_gate.py`（60 例）固化。
- **记忆**：[[structural-misrecognition-final-gate]]
- **检查点**：翻译队列（待翻译池）不得出现硬结构值/引擎串；任何新提取路径不得绕过 is_actionable_translation 直接进队列。

### B9. UnityEvent/输入动作绑定元数据值泄漏（Dobraminhos 实证 2026-09-02）
- **现象**：GUI 库 1031 条 pending 结构性泄漏全部来自两类「字段值」被 `typetree_display_evidence` 放行——① UnityEvent 持久化回调 `m_TargetAssemblyTypeName` 值 `'GameMaster, Assembly-CSharp'`（目标脚本程序集限定类名，642 条）；② 自定义输入 `m_ActionEvents[].m_ActionName` 值 `'PlayerActionsXbox/Move'`（389 条，含编辑器默认名 `'PlayerInUI/New action'`）。
- **根因**：值恰似短短语（`X, Y`/`段/动作`）→ `_has_sentence_shape`/对象值特征把它当显示文本。字段名是确定性结构证据（UnityEvent 目标/方法名、InputSystem action 名都是反射/运行时按名绑定键），但 typetree 遍历只有 m_Name/m_* 等少数不可变字段名级跳过，事件绑定元数据字段无覆盖。
- **解决方案（双层防线）**：
  1. 提取层：`_EVENT_BINDING_FIELDS`（targetassemblytypename/objectargumentassemblytypename/actionevents/actionname/methodname… casefold 字段名）——typetree `visit` 命中即**整子树 blocked 跳过**（含 m_Calls 数组下全部叶子），不依赖值形态；
  2. 终检层：`models._final_structural_backstop` 追加值形态兜底（rawstr 无字段名）——`_ASSEMBLY_QUALIFIED_VALUE`（`X, Y` 且第二段是程序集段 Assembly-CSharp/UnityEngine/mscorlib/System…）与 `_ACTION_MAP_PATH`（`映射段/动作段`）命中即拒于队列外。
- **反误伤**：`'Hello, world'`（第二段普通词）、`'Save, Load and Quit'`（短语逗号）、`'Attack / Move'`（带斜杠动作提示）不命中——程序集段白名单 + 动作段单斜杠前缀约束。

## C. 翻译质量与审核问题

### C1. 审核引用中间快照致误判
- **现象**：审核报告引用翻译中间快照，与最终写入译文不同 → 3 条误判。
- **根因**：自愈流程（self_heal_format_tags + 占位符修复）在质量门后修正译文，审核环节却记录了修复前的版本。
- **解决方案**：裁决审核不合格项时先对照 `translated.txt` 最终译文；长期方向：审核环节改送自愈后最终译文。
- **记忆**：[[review-snapshot-vs-final-lesson]]

### C2. 术语提示污染（审校四根因之一）
- **现象**：跨游戏 active 词对注入每条审校 prompt → 4B 被教唆「英文应保留原文」，Button→按钮 批量误判。
- **解决方案**：词对按游戏过滤 + 按条目命中注入（term 出现在原文才注入，≤5 条）；保留型词对标「专名保留原文（译中文通称不判错）」；系统提示硬规则禁止「应保留原文」式判错。
- **记忆**：[[review-pipeline-four-rootcauses]]
- **检查点**：任何「注入参考给模型」必须问：注入物与本条文本相关吗？

### C3. 一致性缓存杀重译
- **现象**：批内缓存坏译文后，反馈重译的「与坏译文不同的正确译文」被判 consistency_mismatch 拒绝 → 永不收敛。
- **解决方案**：重译路径 `skip_consistency=True`（覆盖缓存而非拒绝）。
- **记忆**：[[review-pipeline-four-rootcauses]]

### C4. 重译多行候选被门杀
- **现象**：模型稳定输出「左滑\n左移」双候选，单行原文下 newline_mismatch 恒败 → BLOCKED。
- **解决方案**：单行原文取候选首个非空行重验门（`_repair_multiline_candidate`）。
- **记忆**：[[review-pipeline-four-rootcauses]]

### C5. 批审罐头理由幻觉
- **现象**：「译文缺失，仅保留术语参考」成段幻觉（译文实为非空）。
- **解决方案**：可验证主张与事实矛盾时逐条重审兜底（每条目至多一次）。
- **记忆**：[[review-pipeline-four-rootcauses]]

### C6. 术语词对污染（方向/设备单字对）
- **现象**：①审核沉淀把 `Left Paddle→左拨片` 提成 `Left→左摇杆` 单字对 → 20 条污染词对全局强制 → 2077 条好译文被 glossary_mismatch 误杀。②键名词对（RMB 被译「人民币」）错误译文沉淀成 active 词对 → 跨游戏误杀正确译文。
- **解决方案**：①质量门必须有键名强制保留检查（`PHYSICAL_KEY_NAMES` 补 RMB/LMB/MMB + `key_name_mistranslated` + glossary 键名词对豁免）②精确词对优先（原文精确命中词对时子串词对全部跳过）③数据清理走「退休」保留审计痕迹 ④每次新增质量检查要思考：此检查失败是否会沉淀成词对污染下游。
- **记忆**：[[glossary-pollution-lesson]]

### C7. 审核过度——原文低质量/梗文本误杀
- **现象**：故意错拼/网络梗/自嘲文本被 4B 当译文缺陷批判 CRITICAL，重译被同一理由反复拒 → BLOCKED。
- **解决方案**：审核维度 11「原文低质量/梗/自嘲豁免」——只核译文是否传达大意，不得以「原文错拼未修正」判错；真坏译文（完全跑偏/漏译否定）仍拦。机械门侧：低质量原文数字软可省略；键盘噪声判别用功能词骨架守卫（≥2 功能词=真实句子）。

### C9. 卡牌/专有名词术语库（2026-09-02 KoiKoi 全量落地）
- **现象**：花札卡牌名乱翻（Hagi→哈吉、Botan→植物学、Susuki→苏苏基），'Botan no AoTan'→幻觉译文、'Matsu no Kasu'→松之雨、'Yanagi no Gaji'→柳川五郎。

## D. 字体渲染问题

### D1. CFF OTF 伪装 ttf 致 TMP 缺字
- **现象**：插件字体 TMP 链缺 160 常用汉字口口口（Rendezvous 实证 2026-08-17）。
- **根因**：CFF OTF 内容伪装 .ttf 部署，插件 `new Font(fontPath)` 按 TTF 解析 CFF → 缺字。
- **解决方案**：插件字体必须真 TrueType（`SourceHanSansSC-Medium.ttf`）；SDF .asset 是 Unity YAML 资产，插件 AddFontResourceEx/CreateDynamicFontFromOSFont 无法解析，只走静态替换。
- **记忆**：[[font-chain-correction-lesson]]

### D2. 字体需求集污染（KoiKoi 实证 2026-09-01）
- **现象**：runtime gate 报「缺字 1620 个码点」，但实际 CJK 基本区 0 缺失。
- **根因**：`build_required_glyph_set` 从 store 所有条目（含 skipped 的 meta# 假名条目、il2cpp 引擎字符串含控制字符）收集码点 → 需求集被垃圾污染。
- **解决方案**：需求集只从 `is_write_ready` 条目收集（对应 project.py `_font_required_glyph_set` 的正确口径）；skip/meta# 条目不贡献需求集。
- **检查点**：runtime gate 报缺字时先查需求集是否含 skip/引擎垃圾条目。

### D3. 写回字体门默认放行（免实机）
- **现象**：免实机闭环下字体候选永远无法实机验证，GUI 每次写回被 runtime 门拒。
- **解决方案**：GUI `write_all` 默认传 `allow_unverified_font_candidate=True`（WARN 放行；条目完整性仍受 allow_partial 约束，与 runner 一致）。
- **记忆**：[[minato-round2-fixes]]

### D4. D1 复发根治——字体源 CFF OTF → 真 TrueType TTF（2026-09-04）
- **现象**：D1（CFF OTF 伪装 ttf 致 TMP 缺字口口口）在 2026-08-18 单字体收敛后再次复发——收敛时把唯一字体源换成 `NotoSerifCJKsc-Medium.otf`（CFF 轮廓），插件 `new Font(fontPath)` 按 TrueType 解析 CFF → 缺字。**违反「禁止复现」规则的教训：根治必须落到资产与白名单，不能只记文档。**
- **根因**：字体链的部署源本身是 CFF；文档记录了 D1 但资产未替换，收敛操作引入复发。
- **解决方案**：
  1. `scripts/convert_cff_to_ttf.py` 确定性转换器（CFF→glyf，cmap/度量逐字段一致），生成真 TrueType `fonts/SimplifiedChinese/NotoSerifCJKsc-Medium.ttf`（git 白名单追踪）；
  2. `font_support.FONT_OPTIONS` 唯一源改 .ttf；`_LEGACY_FONT_ALIASES` 把旧 OTF/思源路径全部映射到 TTF（旧库自动更正）；
  3. 打包白名单（`scripts/package.py`）fonts/ 只带 SDF_Font_Asset + TTF + TMP_Font_AssetBundles，CFF 禁止再作部署源；
  4. .gitignore 注释明示「CFF OTF 禁止再作插件部署源，见问题集 D1」。
- **验证**：`tests/test_font_pipeline.py` 扩展（TTF-only 链）、`test_font_support.py`（别名映射）。
- **检查点**：任何新字体/字体源接入必须验证轮廓格式（glyf 而非 CFF）；「复发」问题根治必须替换资产本身，仅改代码/文档不算根治。

### E4. 写回后场景卡顿——插件常驻扫描 + 冗余部署双根因（0.38.0 任务1）
- **现象**：写回后游戏场景掉帧卡顿，原版流畅（drova/hickory 等多游戏实证）。
- **根因**（两层）：
  1. **Hanhua.FontFallback 插件 1.4.0**：Update 高频扫描 + 周期协程固定短间隔 + `PatchAllFontProps` 全对象大扫每周期跑 + 诊断 dump（全对象反射扫描）不限次——游戏稳态渲染期间持续做重量级扫描，拖垮帧率；
  2. **deploy_runtime 无条件部署**：静态字体覆盖已完整证明（overall==COVERED）时插件兜底非必需，但仍部署常驻 → 不必要的性能税。
- **解决方案**：
  1. **插件 1.5.0**：空转退避（连续 0 应用 → Update 间隔渐增至 6s、周期扫描 8s；场景加载/awake 即时全扫恢复稳态）；AllFontProps 大扫排程（首次+场景加载必跑，稳态 ≥30s 一次）；诊断 dump 限 3 次（+场景加载）；Harmony set_text 钩子是动态文本主路径（即时补丁，不受退避影响——功能无损）。
  2. **deploy skip-when-COVERED**（`font/pipeline.py`）：静态覆盖 COVERED 且无未认证 dynamic_tmp 消费者 → 跳过插件部署（防御性 any 守卫），warning 留痕。
- **验证**：插件源测试锁定版本与退避逻辑；E2E 套件全绿。
- **检查点**：运行时插件任何新增周期性工作必须带退避/排程；静态覆盖完整时插件不部署；写回后卡顿排查先查插件版本（health 协议 v5 / 1.5.0+）。

## E. 性能问题

### E1. 扫描慢/内存暴涨/翻译越久越卡（六大根因）
1. **扫描小时级**：全树逐文件 sha256 → 大文件改 size+mtime_ns 指纹
2. **内存暴涨**：chardet.detect 全量 → 只喂头部 64KB
3. **翻译越久越卡（O(N²)）**：逐条 SELECT+merge+UPDATE → SQL json_patch 合并 + 批量 IN 回写
4. **术语检查正则重建**：每调用 re.escape+compile → pattern 缓存 + 词元预筛
5. **emit_stats failed 全量重算**：每批 O(N) 扫 entries → `_failures_dirty` 条件重算
6. **审校页搜索无防抖**：每按键全量过滤 → 250ms QTimer 防抖 + 行级缓存
- **记忆**：[[scan-translation-perf-six-rootcauses]]
- **检查点**：后续性能问题先找 O(N²)（逐条 SELECT、循环内 re.compile、每批全量扫）。

### E2. GUI 卡顿：语境卡双重刷新
- **根因**：home_page `_refresh_context_card` 主线程 O(N) 全量 get_entries + entriesChanged 直连 + `_refresh_dashboard` 间接调用双重触发。
- **解决方案**：移后台 Worker（token 防竞态）+ translation_running 挂起（`_pending_context_refresh` 补跑）。
- **记忆**：[[gui-stutter-context-card-rootcause]]
- **检查点**：新页面订阅 entriesChanged 时：重活必须进 Worker + 翻译中挂起；检查是否已被别的刷新路径间接调用。

### E3. 2条/批 慢翻译（KoiKoi 实证 2026-09-01）
- **现象**：设置 batch_size=16，但实际每批完成 1-2 条，很慢。
- **根因**（三层）：
  1. **池空**：pending 1095 条全 confidence=low（il2cpp 引擎字符串）→ `is_actionable_translation=False` → 自动翻译池接近空 → 实际可译条目少。
  2. **进度节流假 emit**：`last_emit_ts` 初始 `0.0`（绝对时间起点），首条完成时 `now-0.0` 恒 >1.5s → 首条假 emit（delta=1），随后批内逐条（间隔 <1.5s）不触发，末条才再 emit → 活动流只见「首条 + 全批」虚批。**已修复**：`last_emit_ts = time.monotonic()` 初始化（batch_translator.py native 路径），消假 emit，进度按真实完成数累计。
  3. **每批 N 条语义**：本地模式走 native 逐条请求（每条一次 `translate_text`），「每批 N 条」只控制进度刷新粒度，不合并模型请求——设置 16 而每批显示 2 = 真实唯一文本就 2 条（去重扇出后短批次），是如实显示非 bug。
- **解决方案**：见 B4（il2cpp 引擎字符串标 skipped 而非 low pending，让池有真条目）。这是治本；进度发射本身是设计行为（本地逐条请求，batch_size 只是刷新粒度）。
- **2026-09-02 收尾（#30）**：KoiKoi 资源文件误译全量修正（obj127 卡名 49 条 + metadata 役名 5 条 manual_correction，'[来源文件]' 幻觉译文根除）；97 条 metadata pending（63 format_template + 34 sentence 引擎残留）人工逐条核对后标 skipped（reason=engine_string_verified），全库 pending=0——**宁漏勿坏**：这 97 条是引擎日志/调试串，绝不进翻译池（B4 吸收层之外的第二道防线）；game_context/game_profile 的 'Play：播放'→'Play：开始'（对齐 BUILTIN 权威）修正；Level0/1 的 EventStateMachine 按钮对象 'Load'/'Menu'（str6/str8，逻辑绑定标识，m_MethodName='LoadLevel, Assembly-CSharp' 附近）回退原文并标 skipped（reason=logic_binding_event_state_machine）——写回绝不改逻辑绑定标识（A5 根因根治，str6/str8 全部 skipped）。
- **检查点**：慢翻译排查先查「自动翻译池是否有足够 is_actionable_translation 条目」再查并发/进度。进度显示异常先查 `last_emit_ts` 初始化与 `done_since_emit` 口径。写回后逻辑绑定对象（EventStateMachine/按钮 m_MethodName）字符串 diff 必须 0 变化。
