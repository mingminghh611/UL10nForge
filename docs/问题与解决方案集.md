## A. 写回安全问题（最高优先级）

### A1. 写回后按键消失/失灵——按钮 m_Name 与显示文本同值被改对象名
- **现象**：写回后「开始/设置/退出」按钮 UI 失灵、游戏卡死无法推进（多游戏实证 2026-08-15）。
- **根因**：按钮对象 `m_Name` 与 `m_text` 同值（"Exit"/"Settings" 等显示词）。rawstr 字节扫描无字段身份，名字+文本两处一起被判 display 翻译写回 → 对象名被改 → 游戏代码按名查找（Find/事件/动画）断裂。
- **解决方案（双层修复）**：
  1. 提取层（`extractor.py`）：代码对象/组件对象中白名单词同值出现 ≥2 处（名字+文本共享结构）→ 全组 `structural` 跳过（reason=`object_name_shared_word`）；单次出现照常翻译。
  2. 写回层（`logic_audit.py`）：`code_heavy_display_word` + `LOGIC_COMPARE_WORDS` + obj_strings 同值 ≥2 → 确定性回退保留原文（`display_word_shared_with_object_name`）；`audit_repeat_consistency` 组内 structural+translated 混排自动全组回退。
- **原则**：宁漏勿坏——此类词几乎都有本地化表副本可翻；写坏对象名是灾难。
- **记忆**：[[button-name-writeback-bug]]
- **检查点**：写回后必须验证 changed MonoBehaviour 的 `m_Name` 0 变化（`tmp_typetree_diff.py`）。

### A2. 背景音乐消失——FMOD 配置类写回兜底依赖 externals 兄弟文件
- **现象**：写回后背景音乐/BGM 消失。
- **根因**：FMOD 配置对象（`fmod_config_object` 类）的语义判定依赖 `_script_class_from_head` 通过 m_Script PPtr 补载同目录 .assets 解析类名。若 externals 兄弟文件不在场，函数静默返回 `''` → semantic_revert=0 → 译文照写 → 配置字段被改写。
- **解决方案**：真实写回走 `copy_game_dir` 全量复制 → 兜底生效；测试/回归必须复制整个 Data 目录的全部 .assets，孤立单文件复现的「失败」结论不可信。模拟旧库条目要在 meta 带 `disposition: translate` 才能走到 `logic_key_evidence` 的 fmod 分支（否则被 `legacy_key_guard` 拦截）。
- **记忆**：[[fmod-writeback-fallback-externals]]
- **检查点**：写回后对象级 diff 中音频/配置对象必须 0 变化。

### A3. CSV 对话表误判 YAML 致黑屏
- **现象**：游戏启动黑屏（Rendezvous 实证 2026-08-17），Player.log 显示 CSVParser 数组越界崩溃。
- **根因**：CSV 表头首列空格 + 对话行含冒号 → `looks_like_yaml_text` 误判 YAML → yaml 按行号重建丢表头 → CSV 列/行错位 → 游戏解析越界。
- **解决方案**：
  - CSV 判定必须排 yaml 前；`looks_like_yaml_text` 硬排除 CSV
  - yaml 条目不做代码行过滤；`apply_format_text` yaml 分支行数守恒保护（重建行数 != 原文行数 → 返回原文宁漏勿坏）
  - `_patch_textasset` yaml 组预检（旧库 yaml 条目丢行 → 整组 rejected `yaml_line_loss_guard`）
- **记忆**：[[yaml-csv-misjudge-black-screen-lesson]]
- **检查点**：黑屏排查先看 Player.log 崩溃栈，别只查 level 文件字节。

### A4. 写回后地毯式审计（通用任意格式）
- **两层审计**（`writeback_audit.py`）：
  - 第 1 层确定性硬闸门（任何 FAIL → needs_rewrite 阻断发布）：字节层（编码/BOM/EOL 守恒）+ 行数守恒 + 结构守恒（JSON 深比树/XML 元素树/CSV 首列/PO msgid/字幕时间码）+ 条目级占位符（{0}/%s/%1$s/{name}/<b>/\n）+ 渲染一致性（store 渲染 bytes == 磁盘写回）
  - 第 2 层审校模型软复核（只审计第 1 层 PASS 且有差异的文件），只记 flag 供人工确认
- **要点**：writer 键字段保护优先（`_KEY_FIELD_NAMES` 含 color/sound/type 等）；markdown marker 守恒；富文本标签豁免；JSON 转义误报抑制。
- **记忆**：[[writeback-audit-generic]]
- **检查点**：写回后自动跑 audit_writeback，needs_rewrite=True 需重写回。

### A5. KoiKoi 写回排查结论（2026-09-01）
- **现象**：用户报「写回后按键消失、背景音乐消失、UI 莫名消失、按键失灵」。
- **调查结论**：写回机制本身安全——m_Name 0 变化、音频对象 0 变化、字体替换正常（legacy Font 48/49/90 → NotoSerifCJKsc）。**真实问题在翻译质量**：
  - obj 127 卡牌名乱翻（Hagi→哈吉、Botan→植物学、Susuki→苏苏基）
  - 幻觉译文（'Botan no AoTan'→'[来源文件] KoiKoi_Data/sharedassets0.assets'）
  - 逻辑标识被翻：obj 2099/2114/2120/2135 的 "Load"（位于 m_MethodName 值 'LoadLevel, Assembly-CSharp' 附近）被译成 负载/读取
  - 错误翻译：'Deck Play'→牌组播放、'Call Koi Koi'→拨打 Koi Koi、'Sounds'→听起来、'Draw'→绘制
- **解决方案**：
  1. 翻译质量 = 写回安全的一部分，必须同时治理
  2. 幻觉译文拦截（译文含"[来源文件]"/路径痕迹 → 拒绝）
  3. m_MethodName 附近字符串保护（逻辑绑定标识不译）
  4. 卡牌术语词库（花札术语表，KoiKoi 专属 BUILTIN）
- **检查点**：所有 changed 对象必须是目标对象；字符串 diff 中不得出现原文消失但译文与原文语义无关的情况。

### A6. 渲染一致性 font_enabled 参数
- **现象**：4 个 .subs 文件 render_consistent 误判 FAIL。
- **根因**：`writer._render` 字体启用时对未译条目做标点归一化，audit `_render_from_store` 未传 `font_enabled` → 同源不一致。
- **解决方案**：`_render_from_store` 补 `font_enabled` 参数同源。
- **检查点**：写回审计渲染一致性要与 writer 同源同参数。

### A7. 写回链路全量审计结论——六层防线逐层验证（2026-09-04，0.38.0 任务4）
- **背景**：用户报「写回后概率出现游戏性 bug」（列举形态：场景卡顿/背景音乐消失/按键消失/UI 消失/场景加载失败/按键失灵/卡死），要求重点加强写回模块。对 `writer.py`（2029 行）、`logic_audit.py`（578 行）、`il2cpp_writeback.py`、`record_writer.py` 全文逐行审计。
- **审计结论：未发现新的确定性漏网路径**。六层防线逐层确认闭合：
  1. **L1 入口门**：`is_write_ready` → `_should_write_entry`（disposition 权威分支，仅 translate 写；localization/role 白名单；us/il2cpp 过 is_code_identifier；legacy guards 仅旧库）。
  2. **L2 写前拦截**：immutable_field_protected（18 字段含 m_Name/m_ControlPath/m_Action/m_ActionMap）、field_path_value_mismatch（current != original 拒）、TextAsset 非 UTF-8 整文件拒（F3）、yaml 行数守恒预检、ink 控制词硬保护、xml CDATA/DOCTYPE 拒（F7）、Addressables CRC 写前预检（源 CRC 必须唯一命中）。
  3. **L3 语义回退**（logic_audit）：type_descriptor / unityevent_binding / obj_is_input_axis / fmod_event_path / fmod_config_object / logic_key_in_code_object / display_word_shared_with_object_name + typetree 字段路径 UnityEvent 信号 + audit_repeat_consistency 组内一致化 + 写回侧 `_mono_object_name_span`（m_Name 跨度兜底）与 `_script_class_from_head`（配置类兜底，旧库 meta 缺失也回退）。
  4. **L4 补丁白名单预演**：`_assert_asset_diff_whitelist`——原位补丁 diff 严格落 span 并集；变长补丁非目标区段子串顺序保留 + 短段漂移 ≤ max_shift 预算。
  5. **L5 重开六重验证**：目标字节 + baseline 全对象 sha256 + immutable 逐值 + C2 非目标叶子 + verify_logic_layer（长度头自证/译文存在性/序列对齐走查）+ DLL #US / IL2CPP C3 全池比对——任何失败整文件拒绝、副本原样。
  6. **L6 编排/原子性**：WriteResult 四态记账（written/rejected/logic_reverted 必须 resolved）+ 尾部兜底未 resolve → rejected + 同卷 TemporaryDirectory + `_atomic_write_bytes`（mkstemp+fsync+os.replace+重试）+ Addressables catalog 写后 CRC 回写（唯一性校验 + 失败回滚）。
- **用户列举故障形态 → 防线映射**（全部闭合）：
  | 故障形态 | 防线 |
  |---|---|
  | 场景卡顿 | 任务1 已根治（E4：插件 1.5.0 退避 + deploy skip-when-COVERED） |
  | 背景音乐消失 | A2 FMOD config 判定 + fmod_event_path/fmod_config_object 回退 + `_script_class_from_head` 写回侧兜底 |
  | 按键消失/失灵 | immutable 18 字段 + UnityEvent 信号（字段路径+值层）+ m_Name 跨度兜底 + display_word_shared_with_object_name |
  | UI 消失 | C2 非目标叶子快照 + immutable 逐值重开比对 + baseline 全对象 sha256 |
  | 场景加载失败 | Addressables CRC 预检+回写（唯一性+回滚）+ yaml 行数守恒 + TextAsset BOM/编码保真 |
  | 卡死 | verify_logic_layer 序列验证 + diff 白名单 + IL2CPP/DLL 重开全池比对 + 整文件拒绝原子性 |
- **检查点**：写回后必跑 `writeback_audit`（A4）；概率性 bug 排查先按上表映射到防线，再对照写回日志四态记账（written/rejected/logic_reverted 计数），不要先怀疑写回字节层（L4/L5 已把字节级破坏压缩到重开验证必拦）。

### A8. 写回模块 0.39.0 AI 参与升级——分诊/证据卡/预演三件套（2026-09-06）
- **背景**：用户瓶颈——提取与写回靠硬规则堆积，游戏越多规则越多但总有遗漏，要求 AI 模型直接参与写回。按《本地 AI 智能写回引擎设计与实施文档 V1.0》+ 本仓分析落地 M1-M4 四阶段（架构瓶颈的根治思路：规则仍做确定性底座，AI 只做「减少误杀的旁路判定」，且 AI 永远只有「跳过/回退」权，绝无「多写」权——错误成本不对称 §15/§40）。
- **新增模块**：
  1. **M1 `unity/structural_fields.py`**：结构字段黑名单单一源（UnityEvent/InputSystem/动作绑定字段路径常量），提取端（B9/B10 整枝跳过）与写回端（logic_audit 终检）共用——两处各写一份必然漂移。
  2. **M2 `unity/writeback_ai_triage.py`**：AI 写回分诊层。写回前对候选池批量判定 allow/review/reject（JSON 判定 + 索引对齐 + 判定缓存按 prompt 版本失效）；**fail-closed**——批内请求失败/输出非法 → 本批一律 review 保守跳过（宁漏勿坏）；模型缺席 → 分诊层整体不参与（Lite 通道行为与 0.38.0 完全一致）。
  3. **M3 二进制对象证据卡**：writer 三条写路径（metadata/DLL/asset）成功落盘即产卡（文件/对象/类型/逐处 原文→译文），审计侧 `_audit_v2_model` 批量送模型四值复核（PASS/STRUCTURE_BROKEN/VALUE_INVERTED/PLACEHOLDER_LOST）；有卡无模型 → model_unavailable 阻断发布（与文本层同口径）。写后审计从「只对文本 diff」升级为「二进制改动也有逐对象证据可查」。
  4. **M4 `unity/writeback_plan.py` 写回预演（Dry Run，§62）**：~~已上线~~ **0.41.0 删除**（用户指令：写回预演没必要存在）。核心模块与 UI 按钮整体移除；分类链单一来源原则（M1-M3 仍遵守）不受影响。
- **规则**：
  - AI 分诊只有「移出写回流」的权力（review/reject），没有「放行本该拒绝条目」的权力——放行不覆盖任何确定性闸门（warn 级照写不受分诊影响）。
  - 分诊模型探测失败 = 不启用（与写回 `write_all` 同源探测，Lite/无模型环境零行为变化）。
- **记忆**：[[writeback-ai-upgrade-0-39-0]]
- **检查点**：`test_writeback_ai_triage.py`（23 项）/ `test_writeback_v2_evidence.py`（16 项）+ `test_ui_workbench.py::test_dry_run_feature_removed`（预演不复活回归）。

## B. 识别与文本分类问题

### B1. 识别哑信号——跳过是哑信号，覆盖率≠遗漏率
- **现象**：UnityScript 程序集整类遗漏 825 条文本（lilys-day-off 实证），0 失败审计仍漏。
- **根因**：被跳过的文本不产生任何可见信号；启发式是在见过的样本上拟合的模式，对未见形态直接失明。
- **解决方案**：
  1. 文本载体形态显式清单化（C#/UnityScript/Boo/IL2CPP/typetree/原始串）
  2. 审计口径升级为召回率（真实文本全集 vs 进池文本）
  3. 扫描报告加形态级 skipped 率告警
  4. 用户实测发现的遗漏 → 真实样本 fixture 资产化
- **记忆**：[[recognition-silent-miss-lesson]]

### B2. SetText 等引擎方法不贡献 code 信号致对象名误译
- **现象**：level0 obj 3311 的 `audio`（GameObject 名）被译成「音频」写回 → 游戏按名查找失败（minato 实证 2026-08-15）。
- **根因**：SetText 在引擎串过滤中不贡献 code 信号 → is_code_heavy=False → 对象名被 display 放行。
- **解决方案**：`_CODE_DRIVEN_METHODS`（SetText/SetActive…）计入 `direct_code_signal_count` → is_code_heavy → 对象名跳过。静态按钮对象（控件状态证据）不受影响（对照组测试锁定）。
- **记忆**：[[minato-round2-fixes]]
- **检查点**：引擎串过滤会吞掉对象级信号——对象判定信号必须在完整 scanned 池上算。

### B3. 多语言词典 19 倍浪费 + 键被译坏
- **现象**：electric-trains 内置 19 张同结构语言词典 TextAsset，旧管线全提取 → 19 倍浪费 + 键被译坏（missions=→任务= 断查找）。
- **解决方案**：组内只提取第一张表、其余留档；KV 行只提取值（键保真）；KV 词典判定要求键含字母。
- **记忆**：[[recognition-corpus-and-il2cpp-dumper]]

### B4. il2cpp 引擎字符串污染（KoiKoi 实证 2026-09-01）
- **现象**：pending 1095 条全 low confidence（il2cpp_sentence 611 条引擎日志 + il2cpp_format_template 484 条引擎模板），自动翻译池接近空 → 每批 1-2 条慢翻译。
- **根因**：il2cpp 引擎字符串（Unity 引擎日志/模板）被识别为可翻译条目但 confidence=low，既不能自动翻译也不该被翻译。
- **解决方案**：
  1. il2cpp_sentence/format_template 分类改进：引擎字符串标 `skipped`（原因=engine_string）而非 low pending
  2. 非 UI/非 display 的引擎日志/模板不进翻译池
  3. 进度发射逻辑保持（done_since_emit>=batch OR 1.5s 节流），但前提是池里有真条目
- **检查点**：翻译页「每批完成条数」应稳定 ≈ batch_size 或真条目吞吐；不要出现长时间 1-2 条。

### B5. CSV 判定顺序（见 A3）
- CSV 判定必须排 yaml 前。

### B6. 识别「不需要翻的不用翻」
- **原则**：识别彻底全面 + 精确筛选需要翻译的问题。署名/来源文本（如 KoiKoi 的音频素材 CC0 许可证署名）不是 UI 文本，不应 disposition=translate。
- **检查点**：扫描结果中署名/许可证/调试日志不应出现在翻译池。

### B8. 结构性文本误识别进队列——翻译前最终兜底闸门（2026-09-02）
- **现象**：工具易把 Key/ID/GUID/路径/文件地址/变量名/类名/资源名/Animator State 等结构性文本识别成待翻译文本；翻译后游戏按键失效/UI 消失/背景音乐丢失/卡顿（与 A1/A2 的写回安全同源，但根因在识别层多路径放行）。
- **根因**：识别有多个提取路径（rawstr 字节扫描 / typetree / mono #US / il2cpp metadata / TextAsset json/csv/kv / ink），各自独立分类，历史上一度出现某条路径把结构文本误标 `role=display` + `disposition=translate` 放行进翻译队列；`is_actionable_translation` 是全部队列入口（翻译页待翻译池 / runner run_scope / 概览计数）的单一权威判定，但它此前只依赖提取层 meta（role/disposition/confidence），对「提取层误标」无兜底。
- **解决方案**：`models.is_actionable_translation` 在**任何队列接纳前**追加原文结构终检 `_final_structural_backstop`——原文命中 `is_hard_structural`（URL/路径/GUID/32位哈希/JSON/程序集限定名/纯数字/版本号/混合符号 token）或 `is_engine_string_core`（确定性引擎串：default sprite asset/字体名/Timeline 轨道/FMOD 事件/InputSystem 绑定/hex）→ 一律拒于队列外，无论提取层为何判定。三处保护防误伤：
  1. 键风格标识符（ui_newGame/MENU_PLAY/Level1）**不在闸门职责**（单 token 是上下文决定，由各提取器 should_skip 分层；Level1/Room2 真关卡/对话框名不误杀）；
  2. DISPLAY_WORDS 白名单豁免（'2d'/'3d' 命中 hex 形态但真 UI 词）；

### B16. UTF-16 TextAsset 被二进制过滤整文件跳过 → 对话全漏提（snowday 实证 2026-09-05）
- **现象**：文本提取量极少。snowday DialogueStructure（resources.assets#46）是 UTF-8 BOM + UTF-16LE 双 BOM 头 `b'\xef\xbb\xbf\xff\xfe'` 的 '|' 分隔对话表（134 条西语对话），被 textasset_binary 判定整文件跳过——UTF-16 每隔一字节一个 \x00，NUL 占比 ~0.5 远超 0.05 阈值，二进制过滤在 decode 之前先命中。

- **验证**：`tests/test_b15_b16_snowday.py` 6 例（le/裸 be/双 BOM 提取 + 真二进制对照 + 写回 BOM 保持/无译文原样）。
- **检查点**：二进制过滤任何阈值调整前必须想「UTF-16/32 等宽编码会不会整类误杀」；新增编码支持必须提取/写回对称 + BOM 形态保持。

- **现象**：提取与写回都"成功"，游戏内对话仍是英文。snowday 表 ID|Notes|ActionEvents|Name|ChoicesLink|Spanish 唯一语言列是 Spanish（内容是英语），游戏运行时只读这一列；默认写回追加 ChineseSimplified 新列玩家永远看不到。

- **解决方案**（自动覆盖源列判据，安全边界宁漏勿坏）：`extract_csv_text` 在 `target_col=None` 时检测——数据行 ≥8 + 语言列非空数 ≥行数一半 + 句子态（`_sentence_ratio` ≥0.5，标识符列天然 0）唯一 → source_col 改选该列 + `overwrite_source=True` + 写回列=源列。中文目标列在场不触发（写中文列更安全）；行数不足不触发；多句子态列不触发（歧义）。源列选择修正：句子态列唯一时它优先于「非空行数并列取首个」（Name 人名列与 Spanish 并列实证）。`scan_all`/`extract_asset_file` 透传 `csv_overwrite_source` 参数仅供 runner 显式控制；**GUI 默认不传**——自动判据在 `extract_csv_text` 内默认开，显式传 True 会绕过中文列/小表护栏（宁漏勿坏）。
- **验证**：`tests/test_b16b_b16c_csv_overwrite.py` 6 例（snowday 触发/Rendezvous CHN 对照/小表对照/人名列不选/写回落 col5 行列守恒/file meta 优先）。
- **检查点**：「写回成功但游戏没变」类问题先查游戏实际读哪一列（类引用/源码检索），再谈提取覆盖；覆盖源列模式写回绝不动表头（不追加列）。

### B16c. TextAsset 内嵌 '|' 表写回按 ',' 重建 → 行结构破坏（snowday 实证 2026-09-05）
- **现象**：模拟写回产出 `pid1|||Mika||How was...,,,,测试X`——译文追加成 ',,,,' 尾巴落进最后一个管道字段，游戏解析错乱。
- **根因**：`apply_format_text` 的 csv 分支 delimiter 只看 file 级 meta，TextAsset 内嵌表调用只传 `{"kind":"textasset"}` → 缺省 ','，与表的真实分隔符 '|' 不一致；csv.writer 按 ',' 重建整行结构。
- **解决方案**：提取端 delimiter 留档每条条目 meta（`extract_csv_text`）；写回端三级取值：file 级 meta.delimiter → 首个条目 meta.delimiter → 后缀缺省（tsv/psv/其它）。任一层命中即按真实分隔符重建。
- **验证**：`test_b16b_b16c_csv_overwrite.py` 端到端例（writer 同构调用 → 译文落 col5、行数列数守恒、无 ',,,,'）。
- **检查点**：任何「写回重建」路径的格式参数（分隔符/引号/行终止符）必须从提取现场带档，禁止缺省猜测；新增内嵌格式先查 writer 传参链。

### B17. 对话拟声词被键盘噪声规则误杀 → 对话漏提（hickory 实证 2026-09-05）
- **现象**：hickory 真实对话 `'tck – er… everything is broken.'`（玩家可见台词）被判 prefilter_key_identifier 整条跳过；同类形态 'shh – it's fine.'/'psst – over here!'/'tsk tsk, shame.' 均会命中。
- **根因**：`_KEYBOARD_NOISE` 分支 b（纯辅音簇 ≥3）把拟声词 'tck' 当键盘乱按噪声；FUNCTION_WORDS ≥2 豁免够不着——全句只有 'is' 一个功能词。规则视角合理（tck 确实是辅音簇），缺的是「拟声词是内容词」这条知识。
- **解决方案**：`placeholders._INTERJECTION_WORDS`（58 词白名单：tck/tsk/shh/psst/hmm/ugh/grr/meow/achoo/argh… 含常见重复形态）；`is_hard_structural` 键盘噪声分支在 FUNCTION_WORDS 豁免后追加拟声词豁免——句中任一小写词命中即放行（是句子就不是噪声）。噪声守恒：'asdasdasd'/'fdji ijsdijn' 等真噪声仍拦（回归测试双向锁定）。
- **验证**：`tests/test_placeholders.py` 7 个拟声对话样本放行 + 4 个真噪声样本仍拦；四游戏候选池普查（e0449121aa 扩大面 200 抽样 0 假漏）确认这是该面唯一真漏网。
- **检查点**：识别规则新增任何「形状类」拦截（辅音簇/重复/长度）前，先问「真实对话会不会长这样」（拟声词/省略/方言拼写都是内容）；豁免词表进白名单而不是放宽形状阈值（放宽会连带放走真噪声）。

### B18. AI 辅助识别语境注入 + 文本类型标注（N1/N3，0.38.0 识别架构升级）
- **背景**：B14 的 AI 候选层二次分类 prompt 只有裸字符串——4B 模型不知道 '2F' 在 roomName 字段下是楼层名、在 m_Text 下就是显示文本，判定缺证据。
- **N1 语境注入**（`ai_recognition._item_context`）：从提取 meta 渲染确定性证据进每条 prompt 行——field_path 叶子名（跳过数字索引取最后一个字符串段）/obj_has_values（对象内是否有其他显示证据）/script_class/asset_file，各 40 字符截断。零模型成本（提取器已留档），prompt 只增 ~30 字符/条，40 条批 ≈872 字符远在 ctx 预算内。语境只是证据提示，判定权在模型，本地预校验（is_key_style_identifier + is_actionable_translation）继续兜底。
- **N3 文本类型标注**：verdict schema 扩展可选 `t` 字段（dialogue/ui/quest/item/menu/system），`_parse_verdicts` 返回 dict[int, dict]（JSON 与正则兜底双路径都解析 t，非法值丢弃），升格条目落库 meta.ai_note.ai_text_type——审计端复核口径与翻译端语境可消费。
- **N2 结论（候选白名单不扩大）**：四游戏普查实证——rawstr skipped 中 obj_has_values 的表面（script_class_config/prefilter_engine_string/prefilter_key_identifier）几乎全是正确跳过的确定性证据（输入绑定 '<Gamepad>/leftStick'、字体 GUID、URP 混合模式、TMP 样式表名、timeline track 名、LOCA 表键、'*Fleisch braten (1x)*' 之外全是 *_de/*_en 表键）；e0449121aa 扩大面 15014 条抽 200 人工判据 0 条词组形态真文本。AI 无权推翻确定性判定，扩大收集面只引入噪声——真漏网由确定性闸门修复（B17 即实证），白名单保持 {typetree_candidate, typetree_prefilter}。
- **验证**：`tests/test_ai_recognition.py` 16 例（新增语境渲染 3 例 + t 解析/落库断言）；全量 3165 passed。
- **检查点**：AI prompt 注入的语境必须是提取现场的确定性事实（字段名/类名/文件名），禁止把模型推断写进语境（会变成自我实现预言）；verdict schema 扩展字段必须「可选 + 非法丢弃」——旧模型输出不含 t 不能破坏解析。

### B19. 单字母数字 UI 碎片词被 F49 误杀 → 显示层漏提（hickory 实证 2026-09-05）
- **现象**：真实 AI 识别验证（N2 普查交叉核对）发现 '2F'（楼层指示）在 hickory m_text（display 层）被 F49 单字母规则硬拦——从未进 AI 层；普查扩大到 4 游戏：a61ae49375 'x2'/'2x'/'1x'/'0x'（倍数标记，m_Text）14 条、dcdb50a165 '2H' 时长标签 12 连 + '1P'/'2P'（人数）6 条。均为玩家可读 UI 短语，非二进制残留。

- **验证**：`tests/test_placeholders.py` F50 断言组（11 词放行 + F1/A1/x7/n۶? 守恒仍拦）；模块 149 passed；全量 3165+ passed。
- **检查点**：新增形状类拦截规则时必须用真实游戏显示层（m_text/m_Text）样本对照「玩家可读 UI 短语」形态（楼层/倍数/时长/人数是高频重灾区）；豁免一律走 DISPLAY_WORDS 白名单而非放宽阈值；白名单新词必须验证 is_key_style_identifier=False 防下游键名门穿透。

### B20. 组合绑定引擎串 pattern 无空白约束 → 跨 token 句子标点被当绑定误杀（wicked/Rendezvous 实证 2026-09-05）
- **现象**：wicked 菜单热键 '&137 Save & Quit'（m_Text，&后字母=Windows 快捷键标记）被 typetree_display_field(high)+display 判定后仍在队列入口被拦、终态 skipped；Rendezvous ink 对话行 '^Man: Cooking Oil; Sold! Standard Rice; Sold! …' 同因进 skipped。两者都是玩家可读显示文本。
- **根因**：`_ENGINE_PATTERNS` 的 `[;&].*[;&]` 意图拦「Keyboard&Mouse;Gamepad 组合绑定」，但未约束分隔符间禁空白——跨 token（空格隔开）的 ;/& 是句子标点/热键标记，不是单 token 内的绑定连接符。该 pattern 在队列终闸 `_final_structural_backstop`（is_engine_string_core）生效，把提取层已正确判 display 的条目推翻（双重判定中最严者胜）。
- **解决方案**：pattern 改为 `[;&]\S*[;&]`——只拦**单 token 内** ≥2 分隔符的组合绑定链。单 & token（'Keyboard&Mouse'）本由 `_ENGINE_STRINGS_LOWER` 字面表拦截，行为不变；'&137 Save & Quit'/'Cooking Oil; Sold!' 形态放行。
- **验证**：`tests/test_v2.py::test_is_engine_string` 扩展（3 条误杀样本放行 + Keyboard&Mouse;Gamepad/Keyboard&&Mouse 守恒仍拦）；engine/binding 相关 29 passed；全量 3165 passed（1 个 write 测试为并行运行偶发，单跑通过）。
- **检查点**：队列终闸（_final_structural_backstop）与提取层判定不一致时，必查「提取层判 display 却被终闸拦」的哑信号——skipped.txt 中 reason=typetree_display_field/ink_dialogue_line 且置信度 high 的条目是排查入口；引擎串 pattern 加新形态时必须同时写「守恒仍拦」与「真实文本放行」双向断言。

### B22. 识别覆盖率六根因——AI 升格 kind 不可写回/rawstr 原生文本类型无回退/显示字段判定太窄/高频哑信号吞 UI 词/重复位置误跳过（八库普查 2026-09-07）
- **现象**：开局菜单 UI（开始游戏/继续）、首场景可见英文大量漏识别；八库全量普查（~/.hanhua_sweep/projects 8 游戏库）实证三类真实漏网：
  1. **0.38.0 以来所有 AI 升格条目从未写回成功**——升格 meta 把 kind 改成 "ai_upgraded"，而 writer `_select_write_items` 按 meta.kind 精确匹配分发分支，每条在 v2 尾部循环被拒 "locator_not_found_or_unchanged"（无任何告警的哑失败）；
  2. m_Text/m_text 等**原生文本类型 typetree 解析失败时无 raw scan 回退**，整对象文本丢失；
  3. typetree 叶子字段名判定只认精确集合（m_Text/m_text），**驼峰/装饰变体**（mRoomName/headerLabelContent）漏判显示字段；
  4. prefilter 高频哑信号把 **DISPLAY_WORDS 白名单词/_WORD_CASE 单词式**（Health/Start/Equipment/Complete Bow）在非释放对象中吞掉（22380 行/仅 25 distinct 的重灾区）；
  5. 重复位置（同串多位置）一刀切 duplicate_key_position 跳过——'Start Game' 这类**带显示形态的值副本**被当键跳过；
  6. rawstr 侧三类「弱形态判定」reason 存在真实显示文本漏网：identifier_without_display_evidence（drova 德语装备词 Heiltrank/Schwert…）、code_heavy_identifier（'[E] Talk Shopkeeper' 交互提示）、prefilter_high_frequency（Credits/Title/UI 词）。
- **根因**：
  1. AI 识别升格链路（0.38.0）写 meta 时未对齐写回分发契约——kind 是写回的路由键，不是标签；
  2. 提取器 typetree 分支对原生文本类型假设解析必然成功，无降级路径；
  3. 字段名判定是精确集合匹配而非 token 化判定；高频频次是哑信号（跨对象共享），显式白名单证据应优先于频次猜测；
  4. 重复位置无「值副本 vs 键重复」区分——键风格（is_key_style_identifier）才该跳过；
  5. rawstr skipped 的 reason 分两类：确定性证据（word_table/input/timeline/config/type_reference…——N2 结论：抽样几乎全对）与弱形态判定（三类 reason）——前者 AI 无权重判，后者才是 AI 二次分类的正当场景，但候选收集只收 typetree kind。
- **解决方案**：
  1. `_upgrade_meta`：kind 归一到可分发基类（typetree_candidate/prefilter→typetree；rawstr→rawstr），`ai_verdict_source` 留档原 kind，`ai_upgraded: True` 标记；
  2. extractor raw scan 回退：原生文本类型（_NATIVE_TEXT_TYPES）typetree 解析失败 → raw scan 提取；
  3. `_TYPETREE_DISPLAY_FIELD_TOKENS` 常量 + `_display_field_token_hits()`（叶子名拆 snake/camel token，≥2 命中即显示字段），typetree 叶子循环与 has_value_evidence 双接入；
  4. 高频预过滤豁免：`stripped_casefold in DISPLAY_WORDS or _WORD_CASE.match(s)` 不进 prefilter 高频分支；code_heavy 对象的 has_ui_evidence 增加 ui_control_signal；
  5. 重复位置三级判定：键风格→跳过；带显示证据/句式形态（'Start Game'）→ duplicate_display_position 释放（medium/display）；否则保守跳过；
  6. AI 召回面扩到 rawstr：`_RAWSTR_RECALL_REASONS = {identifier_without_display_evidence, code_heavy_identifier, prefilter_high_frequency}` + `_is_recall_candidate()`，collect_candidates 双通道收集；键风格预校验 + is_actionable_translation 终检 + muted 短路照常兜底（fail-closed 不变）。
- **验证**：tests/test_ai_recognition.py（20 项：rawstr 召回面/确定性 reason 排除/B22 kind 归一/rawstr muted）+ test_f29_word_table.py（3 项契约更新：路径变化但终态等价）+ test_v2.py（duplicate_display_position）。
- **检查点**：
  - 写回分发按 meta.kind 精确匹配——任何写 meta.kind 的代码必须保持 kind ∈ {typetree, rawstr, csv, json, yaml, ink, ...} 可分发集合，标签信息放独立键；
  - 原生文本类型对象 typetree 失败必须有 raw scan 回退路径；
  - 高频频次是哑信号：显式显示证据（白名单/单词式形态/语境）优先于频次猜测；
  - 跳过条目按 reason 分层：确定性证据 reason 不给 AI 重判权，弱形态 reason 进召回面；
  - AI 识别链路改动必须跑 test_ai_recognition.py 全量（升格契约有回归锁定）。
- **记忆**：[[b22-recognition-coverage-six-rootcauses]]

### B23. 文本内容 ScriptableObject 被小配置规则误杀 + AI 越权推翻 B21 双语列策略（fake-it 实证 2026-09-07）

- **验证**：tests/test_v2.py 新增 2 项（ScriptableText 布局仿真实 obj39 释放 pending / 未登记类 AnimationPlayableAsset 对照组仍跳过）+ tests/test_ai_recognition.py 新增 1 项（parallel_lang_field 排除）。fake-it 重扫：70 对 140 条 ContentEn 释放 pending，ContentFr 保持 B21 skipped。

  - 确定性策略条目（parallel_lang_field 等）以 candidate 形态留档时，collect_candidates 必须按 reason 排除——AI 召回面只收「弱形态判定」，不收确定性判定；

- **记忆**：[[b23-scriptabletext-smallconfig-and-parallel-lang-ai]]

### B24. code_heavy 对象引擎方法词被 AI 误升格——UnityEvent 事件绑定当显示文本（fake-it 实证 2026-09-07）
- **现象**：fake-it AI 升格 46 条审计发现 4 条错误：4 个 level4 MonoBehaviour（FakeIt.Scene.SurveyObject/AnalysisObject/RedactionObject/PublishObject，对象 3337/3383/4309/4471）的 'Play' 从 code_heavy_identifier 召回面被升格 pending。

- **验证**：tests/test_ai_recognition.py 新增 test_verify_upgradeable_blocks_code_heavy_engine_method_word（拦截 'Play'/'STOP'/' SetActive ' + 三对照组：非 code_heavy 'Play' 可升格、code_heavy 含空格真交互提示 '[E] Talk Shopkeeper' 可升格、code_heavy 按钮标签 'Close' 不在词族可升格）。
- **检查点**：
  - AI 升格结果审计必查 `obj_is_code_heavy=1 ∧ ai_upgraded=1` 子集——code_heavy 对象的升格必须人工过目；

- **记忆**：[[b24-code-heavy-engine-method-ai-upgrade]]

### B25. AI 识别召回面重复形态未去重——高频噪声挤占上限 + 千条同串送模型浪费（drova 实证 2026-09-07）

### B26. 单词+句尾点号被键风格标识符误杀——对话短句 'Listen.'/'Alright.' 降级 skipped（dead-catch 实证 2026-09-07）

- **验证**：7 个受害形态（Listen./Alright./Good./Okay./Sure./No./Yes.）should_skip 全 False；真键（ui_newGame/MENU_PLAY/Assets.Scripts.Foo/phone_call_01/en/UITable_en/FlashlightData）全 True 不变；库回退 dead-catch 4 条 + a61ae49375 1 条 SQL 翻回 pending 留档 b26_revert。测试：test_key_protection 新增 1 组（放行+双对照）、test_v2 降级闸门新增 1 组（句子词不被降级/真键仍降级）。
- **检查点**：
  - 单字符形状类规则（标识符/键风格）改动时必须枚举「自然语言会长什么样」——句尾句号/感叹号/问号是句子的组成部分，不是标识符字符；
  - 'e.g.' 类两字母缩写含中间点，与句子词形态天然区分，无需额外白名单；
  - 全库扫描其他受害者：runner 库 13 库扫描，仅上述 5 条命中（'Unity.'/'Transitions.' 是 code_identifier 代码池条目，不在本修复范围，正确保持跳过）。
- **记忆**：[[b26-sentence-word-period-key-style]]

## C. 翻译质量与审核问题

### C1. 审核引用中间快照致误判
- **现象**：审核报告引用翻译中间快照，与最终写入译文不同 → 3 条误判。
- **根因**：自愈流程（self_heal_format_tags + 占位符修复）在质量门后修正译文，审核环节却记录了修复前的版本。
- **解决方案**：裁决审核不合格项时先对照 `translated.txt` 最终译文；长期方向：审核环节改送自愈后最终译文。
- **记忆**：[[review-snapshot-vs-final-lesson]]

### C2. 术语提示污染（审校四根因之一）
- **现象**：跨游戏 active 词对注入每条审校 prompt → 4B 被教唆「英文应保留原文」，Button→按钮 批量误判。
- **解决方案**：词对按游戏过滤 + 按条目命中注入（term 出现在原文才注入，≤5 条）；保留型词对标「专名保留原文（译中文通称不判错）」；系统提示硬规则禁止「应保留原文」式判错。
- **记忆**：[[review-pipeline-four-rootcauses]]
- **检查点**：任何「注入参考给模型」必须问：注入物与本条文本相关吗？

### C3. 一致性缓存杀重译
- **现象**：批内缓存坏译文后，反馈重译的「与坏译文不同的正确译文」被判 consistency_mismatch 拒绝 → 永不收敛。
- **解决方案**：重译路径 `skip_consistency=True`（覆盖缓存而非拒绝）。
- **记忆**：[[review-pipeline-four-rootcauses]]

### C4. 重译多行候选被门杀
- **现象**：模型稳定输出「左滑\n左移」双候选，单行原文下 newline_mismatch 恒败 → BLOCKED。
- **解决方案**：单行原文取候选首个非空行重验门（`_repair_multiline_candidate`）。
- **记忆**：[[review-pipeline-four-rootcauses]]

### C5. 批审罐头理由幻觉
- **现象**：「译文缺失，仅保留术语参考」成段幻觉（译文实为非空）。
- **解决方案**：可验证主张与事实矛盾时逐条重审兜底（每条目至多一次）。
- **记忆**：[[review-pipeline-four-rootcauses]]

### C6. 术语词对污染（方向/设备单字对）
- **现象**：①审核沉淀把 `Left Paddle→左拨片` 提成 `Left→左摇杆` 单字对 → 20 条污染词对全局强制 → 2077 条好译文被 glossary_mismatch 误杀。②键名词对（RMB 被译「人民币」）错误译文沉淀成 active 词对 → 跨游戏误杀正确译文。
- **解决方案**：①质量门必须有键名强制保留检查（`PHYSICAL_KEY_NAMES` 补 RMB/LMB/MMB + `key_name_mistranslated` + glossary 键名词对豁免）②精确词对优先（原文精确命中词对时子串词对全部跳过）③数据清理走「退休」保留审计痕迹 ④每次新增质量检查要思考：此检查失败是否会沉淀成词对污染下游。
- **记忆**：[[glossary-pollution-lesson]]

### C7. 审核过度——原文低质量/梗文本误杀
- **现象**：故意错拼/网络梗/自嘲文本被 4B 当译文缺陷批判 CRITICAL，重译被同一理由反复拒 → BLOCKED。
- **解决方案**：审核维度 11「原文低质量/梗/自嘲豁免」——只核译文是否传达大意，不得以「原文错拼未修正」判错；真坏译文（完全跑偏/漏译否定）仍拦。机械门侧：低质量原文数字软可省略；键盘噪声判别用功能词骨架守卫（≥2 功能词=真实句子）。
- **记忆**：[[meme-text-review-overflag]]

### C8. 幻觉译文（KoiKoi 实证 2026-09-01）
- **现象**：'Botan no AoTan'→'[来源文件] KoiKoi_Data/sharedassets0.assets' 幻觉译文。
- **根因**：识别把文件名/路径信息当原文喂给模型，或模型输出崩溃。
- **解决方案**：译文含 `[来源文件]`/`.assets`/路径痕迹 → 判定拒绝重译；识别端不把路径/文件结构当文本条目。
- **检查点**：译文不得含原文路径/文件名痕迹。

### C9. 卡牌/专有名词术语库（2026-09-02 KoiKoi 全量落地）
- **现象**：花札卡牌名乱翻（Hagi→哈吉、Botan→植物学、Susuki→苏苏基），'Botan no AoTan'→幻觉译文、'Matsu no Kasu'→松之雨、'Yanagi no Gaji'→柳川五郎。
- **解决方案**：
  1. KoiKoi 专属 BUILTIN 术语表（花札 12 月×4 种 + 役名 + 计分术语），识别到即确定性直填。
  2. 2026-09-02 全量修正落地：obj127 CardSet 64 条卡名（标准花札名：Kasu→素/Tanzaku→短册/Tane→种/Hikari→光 + 十二月组合卡松上鹤/梅上莺/樱上幕…）经 manual_correction 写回终态 + memory 词对 + AgentMemory manual active（26 条词对，防自动翻乱译）；5 条 metadata 役名（猪鹿蝶/花见/手四/月见 + 专名 'Koi Koi' 保留）同步修正。
  3. **组合词对污染预防（_context_preserve_ok）**：组合词对（含空格）仅当 保留型/全大写/纯专名（_PURE_PROPER_NOUN 词表）/通用 UI 短语白名单（_COMMON_UI_PHRASES）时才可全局参考注入——'Deck Play'（牌堆出牌）被提炼成 (Deck, 牌组) 的跨游戏污染根断（术语污染教训 C6 的组合词对扩展）。
- **检查点**：术语库词对必须带语境保护（组合词对才可全局强制，见 C6）；译文不得含原文路径/文件名痕迹；卡名写回后 obj 字符串 diff 必须逐条是标准花札名。

### C10. 审核过严——长文本幻觉式批判 + 元数据回声误判（fromivan 实证 2026-09-06）
- **现象**：优秀译文（"Dear Ivan" 录取信全文）被判「严重问题·幻觉增义」，列出的批评点在原文/译文中均不存在——审核模型对长文本编造问题。
- **根因**：审核 prompt 无长度约束提示 → 模型对长文本倾向「必须找出问题」的幻觉式批判；模型把 prompt 中的元数据（文件/对象/类型标注）当译文内容回声批判。
- **解决方案**（reviewer.py）：发送给模型的译文超长（>800 字符）时追加「长文本按大意与明显错漏评估，逐句臆测视为无效」约束；模型判定含「元数据回声」（引用 file/obj/kind 等标注词为罪证）→ 判定无效按无问题处理（_METADATA_ECHO_MARKERS 过滤）。
- **检查点**：好译文被误判 CRITICAL 时，先核对批评点是否真的存在于原文/译文中——不存在即审核幻觉，按 C10 检查 prompt 约束与回声过滤。

### C11. 正常文本被静默卡住——阻断必须给出具体原因（fromivan 实证 2026-09-06）
- **现象**：普通文本审核后莫名 BLOCKED，用户看不到任何具体理由。
- **根因**：多轮重译失败的条目落 blocked 时只记轮数，没有综合各轮拒绝理由 → 页面/报告只有「已阻断 N 轮」。
- **解决方案**：blocked 时综合各轮审核理由生成具体原因写 meta（review_blocked_reasons），与 rejected_candidate 一起在审校页/报告透出（见 P5 质量门）。
- **检查点**：任何拦截路径（机械门/审核门/阻断）必须留人类可读的具体原因；「卡住无理由」视为缺陷。

### C12. 审核内容未持久化——只在运行日志临时可见（fromivan 实证 2026-09-06）
- **现象**：`[审核] 原文/译文/判定` 只出现在 runner 运行记录（stdout），持久化报告里没有审核内容。
- **根因**：审核判定只 print 不落盘。
- **解决方案**：runner 审核阶段把逐条 原文/译文/判定 写入持久记录（review-report.md / store meta 双落点）；record_writer 统一导出。
- **检查点**：闭环跑完后，不看 stdout 也应能从持久报告中还原每条审核判定。

### C13. 云端 API 链路三处断点——审核/翻译/写回审计未全链路云化（fromivan 实证 2026-09-06）
- **现象**：用户配置云端 API 后链路各段行为不一致：审核 404（base_url 带不带 /v1 两种填法）、runner 崩「本地模型启动失败」假错、写回审计模型层 model_unavailable 阻断发布。
- **根因**（三处独立断点）：
  1. `ReviewModelService.chat` 硬拼固定后缀：openai 恒 + /chat/completions（不带 /v1 → 404）；anthropic 恒 + /v1/messages（用户已带 /v1 → /v1/v1/messages 404）。
  2. runner 无条件实例化 LocalModelManager + ensure_running → 云端用户无本地模型文件 → 假错退 4；`concurrency = runtime.parallel` 解引用未定义 runtime。
  3. `audit_writeback` 按需构建 ReviewModelService 不带 online_cfg → 云端模式 model_unavailable=True → runner 阻断发布。
- **解决方案**：
  1. `ReviewModelService._endpoint_url`（chat 时归一化，与 translator.normalize_base_url 同语义；存储层保持不带 /v1 原样）。
  2. runner 翻译段按 api.mode 分流：云端不建 manager/不 ensure_running、concurrency=api.concurrency、restart 回调云端 no-op。
  3. `audit_writeback` 增加 `online_cfg` 参数透传按需构建的 service；runner 与 GUI translate_page 均 `api.mode == "api"` 时传 `settings.api_config("review")`。
  4. runner `_run_semantic_review` 透传 online_review_cfg → review_entries（首审/4B 反馈重译/复审同一 service.chat 出口）。
- **原则**：云端配置齐全时，审核/重译/复审/写回审计模型层必须全部走云端端点；本地模型缺失不得成为云端用户的阻断或假错。
- **检查点**：`tests/test_p6_cloud_chain.py`（13 项）+ `tests/test_review_server_gpu_choice.py`；新增云端消费方时必须问「这个 ReviewModelService 构建点是否透传 online_cfg」。

### C15. 审核误阻断五根因——数字等值/平行语言列/纯占位符（fake-it 等 5 游戏记录逐条分析 2026-09-07）
- **现象**：5 游戏闭环记录逐条分析，大量正确译文被莫名阻断：
  1. `200.000 readers→20万读者` 被机械门 numeric_mismatch 阻断（AI 已通过）；
  2. fake-it 120+ 条 ContentFr（法语列）被 4B 批审以「原文为法语，译文误译成中文」阻断；

  1. `_number_tokens` 不认欧式千分位点（200.000=二十万）、中文万/亿乘数（50万=500000）、英文 million/billion 乘数 → 数值比对假阳性。

  3. 纯占位符条目（原文只剩变量名）本无可译内容，却进翻译池被反复重译。

  1. quality.py：`_NUMBER_TOKEN_RE` 前置欧式千分位/万/亿/百分比分支 + `_EN_MULT_RE` 预扫描合并 million/billion；`_CN_MULT_RE` 万=1e4/亿=1e8 换算。数量级改变的真误译仍拦。

  3. reviewer.py（C12b）：审核维度 12「源语言认知」——原文不总是英文，译成中文恒是本职工作，「语言错误」类理由永不成立；`_LANGUAGE_ERROR_CLAIMS` 可验证主张过滤 → 批审判定与事实矛盾 → 逐条重审兜底。
- **检查点**：
  - 数字门误杀先查 `_number_tokens` 分支覆盖（欧式点千分位/万/亿/million/billion）；测试 test_numeric_cn_multiplier_and_european_thousands。
  - 平行语言列误杀查 `parallel_lang_field` skipped 留档；审核「语言错误」类阻断必须有逐条重审兜底。
  - 新增字段级跳过必须「样本+skipped_count」留档，不得静默（R5）。
- **记忆**：[[review-overblock-five-rootcauses]]

## D. 字体渲染问题

### D1. CFF OTF 伪装 ttf 致 TMP 缺字
- **现象**：插件字体 TMP 链缺 160 常用汉字口口口（Rendezvous 实证 2026-08-17）。
- **根因**：CFF OTF 内容伪装 .ttf 部署，插件 `new Font(fontPath)` 按 TTF 解析 CFF → 缺字。
- **解决方案**：插件字体必须真 TrueType（`SourceHanSansSC-Medium.ttf`）；SDF .asset 是 Unity YAML 资产，插件 AddFontResourceEx/CreateDynamicFontFromOSFont 无法解析，只走静态替换。
- **记忆**：[[font-chain-correction-lesson]]

### D2. 字体需求集污染（KoiKoi 实证 2026-09-01）
- **现象**：runtime gate 报「缺字 1620 个码点」，但实际 CJK 基本区 0 缺失。
- **根因**：`build_required_glyph_set` 从 store 所有条目（含 skipped 的 meta# 假名条目、il2cpp 引擎字符串含控制字符）收集码点 → 需求集被垃圾污染。
- **解决方案**：需求集只从 `is_write_ready` 条目收集（对应 project.py `_font_required_glyph_set` 的正确口径）；skip/meta# 条目不贡献需求集。
- **检查点**：runtime gate 报缺字时先查需求集是否含 skip/引擎垃圾条目。

### D3. 写回字体门默认放行（免实机）
- **现象**：免实机闭环下字体候选永远无法实机验证，GUI 每次写回被 runtime 门拒。
- **解决方案**：GUI `write_all` 默认传 `allow_unverified_font_candidate=True`（WARN 放行；条目完整性仍受 allow_partial 约束，与 runner 一致）。
- **记忆**：[[minato-round2-fixes]]

### D4. D1 复发根治——字体源 CFF OTF → 真 TrueType TTF（2026-09-04）
- **现象**：D1（CFF OTF 伪装 ttf 致 TMP 缺字口口口）在 2026-08-18 单字体收敛后再次复发——收敛时把唯一字体源换成 `NotoSerifCJKsc-Medium.otf`（CFF 轮廓），插件 `new Font(fontPath)` 按 TrueType 解析 CFF → 缺字。**违反「禁止复现」规则的教训：根治必须落到资产与白名单，不能只记文档。**
- **根因**：字体链的部署源本身是 CFF；文档记录了 D1 但资产未替换，收敛操作引入复发。
- **解决方案**：
  1. `scripts/convert_cff_to_ttf.py` 确定性转换器（CFF→glyf，cmap/度量逐字段一致），生成真 TrueType `fonts/SimplifiedChinese/NotoSerifCJKsc-Medium.ttf`（git 白名单追踪）；
  2. `font_support.FONT_OPTIONS` 唯一源改 .ttf；`_LEGACY_FONT_ALIASES` 把旧 OTF/思源路径全部映射到 TTF（旧库自动更正）；
  3. 打包白名单（`scripts/package.py`）fonts/ 只带 SDF_Font_Asset + TTF + TMP_Font_AssetBundles，CFF 禁止再作部署源；
  4. .gitignore 注释明示「CFF OTF 禁止再作插件部署源，见问题集 D1」。
- **验证**：`tests/test_font_pipeline.py` 扩展（TTF-only 链）、`test_font_support.py`（别名映射）。
- **检查点**：任何新字体/字体源接入必须验证轮廓格式（glyf 而非 CFF）；「复发」问题根治必须替换资产本身，仅改代码/文档不算根治。

### D5. 写回后部分文字极小——字体替换破坏原字体度量/尺寸（fromivan 实证 2026-09-06）
- **现象**：写回汉化后游戏内部分文本渲染极小（其他文本正常）。
- **根因**：字体替换只换字形资源/字体资产引用，未处理原文本对象上与旧字体耦合的尺寸属性（如 TMP 的 font size 由旧字体度量设计，或组件上的缩放字段）；新旧字体 em 尺寸/行高不同 → 相同 font size 渲染大小不一致。
- **解决方案**：字体链按「度量感知缩放」处理——替换时对比新旧字体 unitsPerEm/行高度量，对受影响文本对象按度量比缩放 font size（有限制上限），保持视觉尺寸一致（见 writer 字体路径 font metric scaling）。
- **检查点**：写回后小字排查先查「该文本对象字体资产是否被替换 + 新旧字体度量差」；字体替换回归测试必须含「同 font size 渲染大小一致性」用例。

### E4. 写回后场景卡顿——插件常驻扫描 + 冗余部署双根因（0.38.0 任务1）
- **现象**：写回后游戏场景掉帧卡顿，原版流畅（drova/hickory 等多游戏实证）。
- **根因**（两层）：
  1. **Hanhua.FontFallback 插件 1.4.0**：Update 高频扫描 + 周期协程固定短间隔 + `PatchAllFontProps` 全对象大扫每周期跑 + 诊断 dump（全对象反射扫描）不限次——游戏稳态渲染期间持续做重量级扫描，拖垮帧率；
  2. **deploy_runtime 无条件部署**：静态字体覆盖已完整证明（overall==COVERED）时插件兜底非必需，但仍部署常驻 → 不必要的性能税。
- **解决方案**：
  1. **插件 1.5.0**：空转退避（连续 0 应用 → Update 间隔渐增至 6s、周期扫描 8s；场景加载/awake 即时全扫恢复稳态）；AllFontProps 大扫排程（首次+场景加载必跑，稳态 ≥30s 一次）；诊断 dump 限 3 次（+场景加载）；Harmony set_text 钩子是动态文本主路径（即时补丁，不受退避影响——功能无损）。
  2. **deploy skip-when-COVERED**（`font/pipeline.py`）：静态覆盖 COVERED 且无未认证 dynamic_tmp 消费者 → 跳过插件部署（防御性 any 守卫），warning 留痕。
- **验证**：插件源测试锁定版本与退避逻辑；E2E 套件全绿。
- **检查点**：运行时插件任何新增周期性工作必须带退避/排程；静态覆盖完整时插件不部署；写回后卡顿排查先查插件版本（health 协议 v5 / 1.5.0+）。

## E. 性能问题

### E1. 扫描慢/内存暴涨/翻译越久越卡（六大根因）
1. **扫描小时级**：全树逐文件 sha256 → 大文件改 size+mtime_ns 指纹
2. **内存暴涨**：chardet.detect 全量 → 只喂头部 64KB
3. **翻译越久越卡（O(N²)）**：逐条 SELECT+merge+UPDATE → SQL json_patch 合并 + 批量 IN 回写
4. **术语检查正则重建**：每调用 re.escape+compile → pattern 缓存 + 词元预筛
5. **emit_stats failed 全量重算**：每批 O(N) 扫 entries → `_failures_dirty` 条件重算
6. **审校页搜索无防抖**：每按键全量过滤 → 250ms QTimer 防抖 + 行级缓存
- **记忆**：[[scan-translation-perf-six-rootcauses]]
- **检查点**：后续性能问题先找 O(N²)（逐条 SELECT、循环内 re.compile、每批全量扫）。

### E2. GUI 卡顿：语境卡双重刷新
- **根因**：home_page `_refresh_context_card` 主线程 O(N) 全量 get_entries + entriesChanged 直连 + `_refresh_dashboard` 间接调用双重触发。
- **解决方案**：移后台 Worker（token 防竞态）+ translation_running 挂起（`_pending_context_refresh` 补跑）。
- **记忆**：[[gui-stutter-context-card-rootcause]]
- **检查点**：新页面订阅 entriesChanged 时：重活必须进 Worker + 翻译中挂起；检查是否已被别的刷新路径间接调用。

### E3. 2条/批 慢翻译（KoiKoi 实证 2026-09-01）
- **现象**：设置 batch_size=16，但实际每批完成 1-2 条，很慢。
- **根因**（三层）：
  1. **池空**：pending 1095 条全 confidence=low（il2cpp 引擎字符串）→ `is_actionable_translation=False` → 自动翻译池接近空 → 实际可译条目少。
  2. **进度节流假 emit**：`last_emit_ts` 初始 `0.0`（绝对时间起点），首条完成时 `now-0.0` 恒 >1.5s → 首条假 emit（delta=1），随后批内逐条（间隔 <1.5s）不触发，末条才再 emit → 活动流只见「首条 + 全批」虚批。**已修复**：`last_emit_ts = time.monotonic()` 初始化（batch_translator.py native 路径），消假 emit，进度按真实完成数累计。
  3. **每批 N 条语义**：本地模式走 native 逐条请求（每条一次 `translate_text`），「每批 N 条」只控制进度刷新粒度，不合并模型请求——设置 16 而每批显示 2 = 真实唯一文本就 2 条（去重扇出后短批次），是如实显示非 bug。
- **解决方案**：见 B4（il2cpp 引擎字符串标 skipped 而非 low pending，让池有真条目）。这是治本；进度发射本身是设计行为（本地逐条请求，batch_size 只是刷新粒度）。
- **2026-09-02 收尾（#30）**：KoiKoi 资源文件误译全量修正（obj127 卡名 49 条 + metadata 役名 5 条 manual_correction，'[来源文件]' 幻觉译文根除）；97 条 metadata pending（63 format_template + 34 sentence 引擎残留）人工逐条核对后标 skipped（reason=engine_string_verified），全库 pending=0——**宁漏勿坏**：这 97 条是引擎日志/调试串，绝不进翻译池（B4 吸收层之外的第二道防线）；game_context/game_profile 的 'Play：播放'→'Play：开始'（对齐 BUILTIN 权威）修正；Level0/1 的 EventStateMachine 按钮对象 'Load'/'Menu'（str6/str8，逻辑绑定标识，m_MethodName='LoadLevel, Assembly-CSharp' 附近）回退原文并标 skipped（reason=logic_binding_event_state_machine）——写回绝不改逻辑绑定标识（A5 根因根治，str6/str8 全部 skipped）。
- **检查点**：慢翻译排查先查「自动翻译池是否有足够 is_actionable_translation 条目」再查并发/进度。进度显示异常先查 `last_emit_ts` 初始化与 `done_since_emit` 口径。写回后逻辑绑定对象（EventStateMachine/按钮 m_MethodName）字符串 diff 必须 0 变化。

### F7. 运行信息只存在有界内存视图——事后无法复盘（0.41.0 任务七）
- **现象**（用户实证）：实时处理流和运行记录只能记录部分信息。ActivityFeed `max_items=120` 丢最旧；log_view `MaximumBlockCount=2000` 静默截断；`start()`/切换项目 `clear()`；扫描阶段事件（home_page `_on_scan_progress`）从不落盘；拒绝条目/缺字/警告界面只展示前 10/16 条且无全量记录。翻译几十分钟的长跑，早前批次进度、审核判定、写回审计明细在界面和磁盘上都不复存在。
- **根因**：GUI 运行信息只有两块有界内存 UI，从未设计磁盘持久层；record_writer 是写回后的事后快照，不是运行时间线。
- **解决方案**：`hanhua/core/run_log.py` 单一落盘出口——每项目一个 append-only 日志 `<app_dir>/run-logs/<安全目录名>__<md5[:6]>.log`，按游戏目录绝对路径身份区分；begin_session 分节（开始扫描/翻译/写回/打开项目）；事件行 `HH:MM:SS.mmm [category][status] text`；多行续行缩进；逐条 flush；线程安全；IO 失败静默自禁用（日志是附属功能绝不阻断主流程）；模块缓存共享实例；退出时 `close_all_run_logs()`（main.py aboutToQuit）。接线：home_page `_scan_game_dir`（拖入目录，扫描期 project 未建）与 translate_page `project.game_dir` 同键 → 扫描+翻译+写回一份时间线；translate_page 新增 `_log_line`/`_feed_event` 漏斗（log_view/activity_feed 的全量替身）+ `_runlog`/`_runlog_begin`；拒绝条目/缺字/警告全量落盘不截断。
- **检查点**：① 新增 UI 日志点只调 `_log_line`/`_feed_event`（translate_page）或 `_runlog_event`（home_page），禁止直接调 `log_view.appendPlainText`/`activity_feed.append_event`（会绕过落盘）；② 日志文件 utf-8 非 utf-8-sig（跨会话追加不能叠 BOM）；③ `_scan_game_dir` 必须在 `HomePage.__init__` 初始化（None=不在扫描期），否则 `_runlog_event` 守卫抛 AttributeError 破坏扫描信号回调；④ 退出关句柄只在 main.py 挂 aboutToQuit，不要在测试里依赖。回归测试 `tests/test_run_log.py`（15 例：路径映射/BOM/多行缩进/IO 自禁用/线程安全/UI 漏斗落盘）。
